# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Add durable project-specific notes here as they are discovered through real work.
- `manifest.json` must only contain fields from Obsidian's theme manifest schema (`name`, `version`, `minAppVersion`, `author`, `authorUrl`); there is no `description` field, and Obsidian's theme review flags unknown fields. `scripts/validate-json.mjs` enforces the required-field list, so keep it in sync with the schema, not with whatever fields happen to be present.
- `npm run lint:obsidian-review` (`.stylelintrc.obsidian-review.cjs`) reproduces Obsidian's actual community-theme review "CSS LINT" panel, not the published `stylelint-config-obsidianmd` npm package: that package's `index.js` does `extends: "stylelint-config-standard"`, so running it standalone also reports dozens of stylistic errors (`selector-class-pattern` on Obsidian's own `.HyperMD-*`/`.cm-gutterElement` classes, `selector-not-notation`, `no-descending-specificity`, `property-no-vendor-prefix` on `-webkit-mask-*`, etc.) that the review itself never surfaces. The review bot (`obsidianmd/obsidian-workflows`, `src/lint.ts`, `SCANNER_STYLELINT_CONFIG`) runs stylelint with no base config at all — only its own 13 explicit rules — so `.stylelintrc.obsidian-review.cjs` reproduces that object directly instead of extending the npm package. It also recomputes the `plugin/no-unsupported-browser-features` target Electron version from `manifest.json`'s `minAppVersion` the same way the scanner does (flags CSS features, e.g. `css-masks`, unsupported by that Electron's Chromium on *both* the unprefixed and any vendor-prefixed declaration — a `-webkit-` fallback alone won't clear it; raise `minAppVersion` or avoid the feature instead). Keep this file's rules in sync with upstream `src/lint.ts` if Obsidian changes the review (version/commit cited in the file's header comment).
- CI (`.github/workflows/validate.yml`) runs `npm run validate` (manifest/variant JSON shape), `npm run lint:css` (this repo's own relaxed `.stylelintrc.json`, a stricter day-to-day style lint, not what the review checks), and `npm run lint:obsidian-review` (must stay green — it's what blocks a real theme submission).
- Each dark/light variant's `--kanso-*` overrides live in `theme.css` near the `@settings` block (around line 70 on `main`). A new variant needs: an entry in the `@settings` class-select list, a selector-list addition so `.theme-light.<variant>` forces the dark palette, a `.theme-dark.<variant>, .theme-light.<variant> { --kanso-bg0..bg4 }` block (match that compound-selector specificity, not a bare `.<variant>` rule, or the base block's `.theme-light.<variant>` entry silently wins and the variant falls back to Zen's colors when forced while Obsidian itself is in light mode), a `:not(.<variant>)` addition to the Pearl/light fallback selector, and (for dark variants) an addition to the `.theme-light.<dark-variants>` accent block. Also add `variants/<variant>.json` (`{"class","name","mode"}`) for Obsidian's variant picker.
- Obsidian's own editor CSS targets CodeMirror/Live-Preview elements with selectors like `.markdown-source-view.mod-cm6 .cm-scroller`, `.cm-s-obsidian .cm-inline-code`, `.cm-s-obsidian .HyperMD-codeblock`, and `.inline-title:not([data-level])`. A theme rule on the bare class (`.cm-scroller`, `.cm-inline-code`, `.inline-title`, etc.) loses the cascade silently in Live Preview even though it works in Reading view; match Obsidian's selector (or specificity) to win. The same silent-loss trap applies to community-plugin stylesheets: a plugin's own rule on the identical selector, loaded after the theme, wins ties and resets any longhand (e.g. `border-bottom-color`) a later shorthand (`border-bottom: solid`) on that plugin's side doesn't explicitly repeat — verified against Dataview's header-row border. Raise specificity with a real ancestor selector (not `!important`) to win regardless of load order.
- Obsidian's CM6 editor marks the current line with `.cm-line.cm-active` and `.cm-gutterElement.cm-active` (plus `.cm-editor.cm-focused` on the wrapper while focused) — not upstream CodeMirror's `.cm-activeLine`/`.cm-activeLineGutter`. A rule that sets `background-color` on the active line also overwrites any background the line already has (e.g. code block lines carry `--code-background`), inverting the highlight direction inside fenced code; use `background-image: linear-gradient(color, color)` instead so it composes with the element's own background.
- Plugin companion styling: Dataview, Kanban, and Calendar already inherit Kanso's palette almost entirely through Obsidian's own shared CSS variables (`--table-*`, `--background-*`, `--text-*`, and, for Calendar specifically, its own `--color-*` variables which fall back to Obsidian's accent/text variables) — verified live via a CDP-driven Obsidian instance, not just by reading each plugin's source. Only small, targeted selectors were needed on top. Excalidraw is the exception on two fronts: with its own "Match Obsidian theme" setting on (or once a drawing's theme has been toggled at all), the plugin writes its entire UI color palette as an inline `style` attribute on `.excalidraw` every time a drawing opens. These are CSS custom properties, which inherit, so a plain rule on `.excalidraw`'s own direct children (the top/bottom toolbar containers and the context-menu/eye-dropper layers Excalidraw renders its islands and popups into — `.excalidraw.theme--dark > *` / `.excalidraw:not(.theme--dark) > *`) beats the ancestor's inline value without `!important`: a normal rule on a descendant always wins over a value only inherited from an ancestor's inline style. The canvas itself is completely unreachable from CSS: Excalidraw paints it onto a `<canvas>` element and, with theme-matching on, substitutes its own fixed default dark (`#121212`)/light (`#ffffff`) fill, ignoring both the drawing's saved `viewBackgroundColor` and every CSS custom property — confirmed by sampling the actual rendered pixel, not just reading computed styles. Don't claim a theme recolors the canvas; say plainly that it can't.
- The reading view's actual scroll container is `.markdown-preview-view` (a child, `overflow-y: auto`), not `.markdown-reading-view` itself (`overflow-y: visible`, sized to the visible pane by its flex/grid layout parent, not to content height). A `position: fixed` element needs its containing block set on the non-scrolling `.markdown-reading-view` wrapper (via `contain: layout` or an equivalent transform) to center within the visible pane regardless of scroll offset; setting it on the scroller itself would resolve percentages against the full scrollable content box instead.
- To visually test `theme.css` in a real Obsidian when no FUSE/X server is available: extract the AppImage (`./Obsidian.AppImage --appimage-extract`, since mounting needs FUSE), then run the extracted `squashfs-root/obsidian` (or `squashfs-root/AppRun`) binary with an isolated `HOME=<scratch dir>` (Obsidian's vault registry lives under `$HOME`, shared with any other Obsidian instance using the same `$HOME`), `--no-sandbox --disable-gpu --disable-dev-shm-usage --ozone-platform=headless --enable-features=UseOzonePlatform --ozone-override-screen-size=WIDTH,HEIGHT --remote-debugging-port=PORT --user-data-dir=<profile>`. Plain `--headless` or `--window-size` do not produce a usable framebuffer; the actual window size instead comes from `<profile>/<vault-id>.json`'s `width`/`height` fields (edit that file, rely on `--ozone-override-screen-size`, or call `window.electronWindow.setBounds({x,y,width,height})` once connected, for a usable viewport). Register the test vault once by writing `<profile>/obsidian.json` with `{"vaults":{"v1":{"path":"<vault>","ts":<ms>,"open":true}}}` before first launch so it opens straight into the vault instead of the picker; if it still lands on `starter.html`, call `window.electron.ipcRenderer.sendSync('vault-open', '<path>', false)` via `chrome-devtools-axi eval` (the "Open folder as vault" button triggers a native OS file dialog that CDP cannot drive). Drive it with `chrome-devtools-axi`, using your own `--remote-debugging-port`/`--user-data-dir` and a unique `CHROME_DEVTOOLS_AXI_SESSION`, since concurrent Kanso tasks run their own Obsidian instances and the tool's default session/port is shared. Settings (and the Style Settings plugin UI) open in a *separate* CDP page/window (title `Settings - ...`), not a DOM modal in the main page. Switch themes/variants from the console with `app.changeTheme('obsidian'|'moonstone')` for dark/light base and `document.body.classList.add('kanso-zen'|'kanso-ink'|...)` for a variant, and switch edit/reading mode with `leaf.setViewState({type:'markdown', state:{...leaf.view.getState(), mode:'source'|'preview'}})`. `emulate --viewport` has been observed to break subsequent `screenshot` calls in this headless setup, prefer sizing the real window instead; also, the window chrome (the native title-bar button row specifically) can render a stale/cached frame in screenshots that does not reflect live DOM changes, so verify title-bar CSS via `getComputedStyle`/`pointerEvents` in `eval` rather than trusting that one region of a screenshot. The machine tends to run several of these test instances in parallel under memory pressure; the process sometimes exits on its own (including after `location.reload()`) and expects a relaunch rather than debugging it as a config problem — multiple workers share this machine, so kill only the exact PID you launched, never a broad pattern like a port number or `squashfs-root/obsidian`.
- A theme's `themes/<folder>/manifest.json` is only picked up by Obsidian's `customCss.readThemes()` scan when the manifest's `name` field exactly equals the folder's own name (case-sensitive) — `themes/kanso/` with `"name": "Kanso"` is silently skipped (0 themes installed), `themes/Kanso/` is not. Separately, opening a vault for the first time (or one with disabled plugins) shows a "Do you trust the author of this vault?" prompt; choosing "Browse in Restricted Mode" sets `app.customCss.disabled = true` and `loadTheme()` becomes a no-op (styleEl stays empty) even once a theme is selected and scanned — click "Trust author and enable plugins" (or call `app.customCss.globallyEnable()` from `eval` for a quick headless check) before expecting `--kanso-*` variables to resolve.
- A disposable worktree's `git checkout --orphan <branch> && git rm -rf . && git clean -fdx` (e.g. to build an evidence branch) wipes the *same working tree* `no-mistakes`/CI needs, including `node_modules` — `npm ci` after switching back to the real branch.
- To emulate mobile in that same headless Obsidian: run `app.emulateMobile(true)` in `eval` (the *first* call after launch is a no-op — Obsidian hasn't finished internal setup yet — so call it, then call it again or just re-check `document.body.className` for `is-mobile`/`is-phone`/`is-tablet` before trusting it). Window width decides phone vs. tablet (phone below Obsidian's internal breakpoint, e.g. 390px; tablet above, e.g. 820px) — relaunch at a new `--ozone-override-screen-size`/profile `<vault-id>.json` width rather than trying to resize a live window. Obsidian's own `app.css` (inside `obsidian.asar`, extract with `npx @electron/asar extract`) already sizes its own mobile chrome generously (mobile navbar actions measured ~48x52px, safe-area insets threaded through nearly every mobile surface) — don't add speculative Kanso CSS for those; the real gap is Kanso's own desktop tag padding (`padding-inline: 0.15em`, set for density) carrying over unchanged to mobile and Obsidian tying `--checkbox-size` to the editor font (~18px on phone), both measurable via `getBoundingClientRect()` on `input.task-list-item-checkbox` / `a.tag` / `.cm-hashtag`. Don't fix the checkbox gap by raising `--checkbox-size` itself: Obsidian's own `margin-inline-start: calc(var(--checkbox-size) * -1.5)` positions the box from that same variable, so growing it also shifts the box left past the content margin and desyncs its vertical centering against the label text. Instead add a same-size-as-before `::before` on `input.task-list-item-checkbox`, absolutely positioned and centered (`top/left: 50%; transform: translate(-50%,-50%)`), sized larger than the box but left transparent — a real tap anywhere in that enlarged area still hit-tests to the input (confirm with `document.elementFromPoint(x, y)` inside the enlarged-but-outside-the-visible-box region), without moving or resizing the visible glyph. Note for testing: a non-trusted `dispatchEvent(new MouseEvent('click'))` does *not* run a checkbox's native toggle in Chromium (only `.click()` or a real trusted input does), so use `elementFromPoint` hit-testing, not a dispatched click, to verify an enlarged tap zone actually routes to the input.
